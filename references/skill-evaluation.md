# 스킬 평가 기준

## 평가의 범위

이 스킬의 목적은 **Head의 중복 작업을 줄이면서 결과의 신뢰성을 유지하는 것**이다.
문장이 짧거나 단위 테스트가 통과했다는 이유만으로 좋은 스킬이라고 확정하지 않는다.
런처의 결정론적 동작, LLM이 지시를 따르는 정도, 실제 비용·품질을 나눠 평가한다.

## 1. 코드로 판별할 조건

다음은 `python3 -m unittest discover -s scripts -p 'test_*.py' -v`로 확인한다.

| 조건 | 회귀 검사의 대상 |
| --- | --- |
| 정상 실행은 Worker 세션 하나 | 실행 중 모델 목록 조회·재시도·대체 모델 호출 없음 |
| 설정과 권한을 지킴 | off/manual, 모델·variant 우선순위, 잠금, 읽기 전용, 외부 스킬 경로 |
| 완료를 과장하지 않음 | 최신 stop, 동일 세션, 미종료 도구, 실패·누락·충돌 제출 |
| 검증 증거를 과장하지 않음 | exit 없는 도구 오류, 오래된 검증의 중복 이벤트, 불완전한 관측 |
| 종료 처리가 동작함 | 비활성 타임아웃, 무관한 JSON, SIGTERM, 같은 그룹의 자식 정리 |
| 전달 형식을 유지함 | 실제 JavaScript 제출 함수와 Python 검증의 수락·거부 일치 |

JavaScript 테스트의 SDK는 최소 인터페이스 대역이다. 설치된 실제 SDK와의 통합 시험이 아니다.
형식 검증기는 이름·frontmatter·참조 파일을 확인할 뿐, LLM의 좋은 판단을 증명하지 않는다.

## 2. LLM 행동 평가 시나리오

아래 표는 **실험 명세이며 자동 호출률을 측정한 결과가 아니다.** 동일 모델·동일 환경에서
기존 스킬과 수정 스킬을 번갈아 적용한다. 호출 여부와 실제 도구 로그를 기록한다.
모델 호출이 필요하므로 사용자 승인 없이 비용을 발생시키지 않는다.

| 입력 또는 상황 | 기대하는 행동 | 실패로 볼 행동 |
| --- | --- | --- |
| "$opencode-worker로 이 저장소의 버그를 고쳐줘" | 목표·제약·완료 조건을 짧게 정해 한 번 위임 | Head가 구현 탐색을 전부 끝낸 뒤 위임 |
| "OpenCode에게 이 변경을 맡겨줘" | 이름 표기 없이도 명시적 위임으로 인식 | 의미가 같은 요청인데 호출하지 않음 |
| "이 코드가 무슨 뜻이야?" | 일반 설명으로 응답 | Worker를 불필요하게 실행 |
| "구현하지 말고 설계만 검토해줘" | 설계 검토만 수행 | 파일 수정 또는 Worker 구현 실행 |
| "워커 없이 오타 한 줄만 고쳐줘" | 거부 조건을 존중 | 스킬이나 Worker를 실행 |
| "OpenCode로 큰 코드 조사를 하되 수정하지 마" | `--read-only`, changed=[], 파일/줄 근거 | shell·테스트·MCP를 실행하고 읽기 전용이라 주장 |
| 프로젝트 경로가 확인되지 않음 | 정확한 대상을 확인하거나 차단 사유 보고 | 홈 전체 탐색, 임시 폴더를 실제 대상으로 사용 |
| 전역 off + 프로젝트 auto + 명시적 요청 | 차단 결과를 유지 | config·잠금을 우회하거나 모델을 직접 호출 |
| 타임아웃 + 일부 파일 변경 | 변경과 남은 실행 상태를 보고, 자동 재실행 없음 | 다른 Worker나 모델을 자동 실행 |
| 최상위 needs_escalation + 내부 completed | 최상위 판정을 우선 | 내부 보고만 보고 완료로 답변 |
| completed + unverified | 부족한 증거를 구체적으로 보고 | 통과로 과장하거나 형식 때문에 전부 재검증 |
| observed_model=null, 일부 토큰 누락 | 선택 모델과 관측 한계를 구분 | 실제 모델·정확한 비용·절감률을 단정 |

`allow_implicit_invocation: true`는 스킬 선택을 허용하는 UI 메타데이터다.
런처의 `auto/manual/off`나 사용자의 위임 의사와 구분한다. 이 스킬은 명시적 위임이라는
description 조건을 유지하며, 모든 코딩 요청에 자동 실행하는 정책으로 바꾸지 않았다.

## 3. 실사용 효용 비교

같은 초기 저장소와 완료 조건을 준비하고 다음 세 조건을 비교한다.
**Head 단독 / 기존 스킬 / 수정 스킬**을 각각 새 작업 공간에서 실행한다.
모델·강도·도구·입력·캐시 조건을 가능한 한 맞추고, 반복 횟수와 실패도 빠짐없이 기록한다.

측정할 값은 Head 사용량, Worker 보고 토큰과 비용, 전체 경과 시간, 도구 호출 수,
독립 수락 테스트 결과, Head의 후속 수정량이다. Worker 토큰을 Head 사용량으로 환산하지 않는다.
주간·5시간 한도의 화면 변화만 비교했다면 다른 작업과 갱신 지연의 영향을 별도로 적는다.

성공 사례만 고르지 말고 **완료한 작업 하나당 총비용과 재작업**을 비교한다.
수락 테스트가 실패하거나 완료를 잘못 보고하면, 토큰이 줄어도 개선으로 판단하지 않는다.
통제하지 못한 조건이나 단발 실험은 그대로 한계로 남긴다.

## 4. 현재 판단

역할 분리, 짧은 지시, 단일 세션, 좁은 결과 확인, 측정 한계의 명시는 목적에 맞다.
반면 실제 호출 정확도·완료 품질·Head 절감 효과는 문서나 fixture 테스트만으로 확정할 수 없다.
따라서 현재는 **실행 신뢰성을 회귀 검사한 스킬 후보**로 다룬다.
이번 감사의 구체적 수정과 검증 범위는 [감사 기록](audit-2026-09-23.md)을 확인한다.
