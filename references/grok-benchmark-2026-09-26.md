# Grok Build Worker 실사용 비교 — 2026-09-26

## 조건

- 환경: Windows 네이티브, Grok Build CLI 1.0.41, Python 3.13.14.
- 모델: Grok CLI 기본 `grok-4.7`. 두 실행 모두 `--permission-mode auto`, `--no-plan`,
  `--no-subagents`, `--output-format streaming-json`을 사용했다.
- 직접 CLI와 `lite.py run --engine grok`를 각각 독립된 동일 초기 Git 저장소에서 한 번씩 실행했다.
  프롬프트의 작업 내용은 같고 절대 저장소 경로만 다르다. 직접 실행이 먼저였다.
- 작업: `normalize_tags(values)`가 공백 제거, 소문자화, 빈 항목 무시, 순서 보존 중복 제거를
  하도록 `tags.py`를 고친다. 저장소 내 단위 테스트와 저장소 밖 독립 수락 검사를 수행한다.
- 수락 검사: 두 실행 결과에서 `normalize_tags`의 빈 입력, 대소문자·공백·중복 조합,
  입력 순서 보존을 확인했다. 각 작업 트리의 변경 파일도 검사했다.

초기 실험에서는 Grok 기본 ask 권한 모드의 편집 요청이 헤드리스 실행에서 취소됐다.
`auto` 모드로 해결했다. 다음 실험에서 실제 수정과 수락 검사는 통과했으나,
중간 진행 텍스트와 최종 JSON을 이어 붙여 결과를 잘못 판정했다. 모델 턴별 `usage`
이벤트로 최종 텍스트를 분리해 고친 뒤 위 표의 새로운 한 쌍을 실행했다.

비용과 토큰은 Grok CLI가 보고한 값이다. 경과 시간은 로컬에서 관측했다.
단발 비교이므로 속도·비용 우위를 주장하지 않는다. 수락 검사는 이 소형 작업의
동작을 확인할 뿐, 임의 저장소에서의 품질이나 권한 모드의 모든 경로를 증명하지 않는다.
앞선 실패를 포함한 원시 CLI 로그는 세션·로컬 경로와 환경 정보가 들어 있어
저장소에 올리지 않았다.
