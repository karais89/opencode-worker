# Grok Build 직접 실행과 두 스킬 Worker 벤치마크 (2026-09-26)

## 목적과 조건

Windows 네이티브 환경에서 동일한 작은 Git 저장소 작업을 Grok CLI 직접 실행과 **설치된** `$grok-worker`로 각각 수행했다. 저장소에는 실패하는 `normalize_tags` 구현과 두 테스트가 있었다. 작업 지시는 공백 제거, 소문자 변환, 빈 값 제외, 입력 순서대로 중복 제거, `tags.py`만 변경, `python -m unittest -v` 통과였다. 두 경로에 동일한 Worker 프롬프트 생성 함수를 사용했으며, 저장소 절대 경로만 달랐다. CLI 모델은 기본값인 `grok-4.7`이었다. Grok CLI 버전은 `1.0.41`; 설치 번들은 `2.1.0`이었다.

실행 시간은 각 프로세스 시작부터 종료까지의 경과 시간이다. 토큰과 비용은 CLI 종료 이벤트 또는 Worker 요약에 실제 표시된 값만 기록한다. 각 실행 후 별도 Python 테스트와 수용 조건 네 가지를 확인했다. 모델 품질과 속도의 통계적 차이를 주장할 만큼 반복하지 않았다.

## 관측 결과

| 시도 | 직접 실행 | 설치된 Worker | 독립 확인 | 해석 |

| 캐시를 무시한 새 복제본 | 98.28초, 정상 종료, 121,354 토큰, $0.167564 | 45.30초, `needs_escalation`, 종료 이벤트·비용 없음 | 양쪽 모두 `tags.py` 수정·테스트·수용 조건 통과 | Worker 실행 중 Grok 정상 종료 이벤트가 없어 완료 판정을 보류했다. 이 시도도 성공 쌍이 아니다. |
| 추가 진단용 새 복제본 | 직접 실행 13.14초 후 실패 | Worker 12.45초 후 실패 | 변경 없음 | 직접 CLI의 stderr에서 HTTP 429 `subscription:free-usage-exhausted`를 확인했다. 무료 `grok-4.7` 사용량의 24시간 이동 한도에 도달했다. |

첫 시도의 캐시 문제는 벤치마크 저장소에 `__pycache__/`을 무시하는 `.gitignore`를 추가하고 양쪽에 동일하게 적용해 해결했다. 마지막 진단에서는 Worker뿐 아니라 Grok CLI 직접 실행도 같은 사용량 한도에 막혔다. 따라서 **깨끗하게 완료된 직접 실행 대 Worker 쌍은 아직 없다.** 두 경로의 시간·토큰·비용 우열을 결론 내리지 않는다.

## 재검증 조건

Grok 사용량이 복구되면 동일한 초기 커밋에서 직접 실행과 설치된 Worker를 각각 새 복제본으로 실행한다. 두 실행 모두 정상 종료, `tags.py`만 변경, 독립 테스트와 수용 조건 통과를 확인한 뒤 결과를 이 문서에 추가한다. 원시 CLI 출력과 임시 저장소는 이 저장소에 포함하지 않는다.
