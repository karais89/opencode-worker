# 2026-09-23 구조·신뢰성·스킬 감사

## 범위

기준은 `karais89/opencode-worker`의 main 커밋
`812e3fae07d95b782453c44cf80e328931074fa5`다. GitHub의 추적 파일 13개를 검토했다.
실행 관련 Python 5개와 asset 2개는 격리 작업 공간에 옮긴 뒤 Git blob 해시가 원본과 같은지 확인했다.
이 원본과 수정본을 분리해 테스트했다. 과거 Full 버전의 테스트 수를 현재 결과로 인용하지 않았다.

단일 Worker 구조를 유지했다. 유료 모델 호출, 자동 재시도, Planner/Reviewer 추가,
사용자 전역 설정 변경, 배포·병합은 하지 않았다.

## 구조 판단

`SKILL.md`는 Head의 판단 절차, `lite.py`는 설정과 실행, `streaming.py`는 관측,
`submission.py`와 JS 도구는 제출 계약, `verification.py`는 검증 명령 대조를 담당한다.
역할 분리는 목적에 맞으며 전체를 새 프레임워크로 바꿀 근거는 발견하지 못했다.
중요한 문제는 모듈 수보다 **완료와 검증 증거를 잘못 인정하는 경계 조건**에 있었다.

## 재현한 결함과 수정

우선순위는 실행 신뢰성에 미치는 영향 기준이다. 외부 공격에 대한 보안 등급이나 악용 확인을 뜻하지 않는다.

| 우선순위 | 기존 문제 | 수정 |
| --- | --- | --- |
| 높음 | 이전 stop 뒤 새 단계·제출이 와도 완료. 세션 ID 없는 종료나 미종료 도구도 놓침 | 새 단계·도구에서 stop 무효화, 세션·도구 ID 검증, 진행 중 도구 추적 |
| 높음 | 선언된 검증 도구가 error인데 exit가 없으면 unverified로 넘어가 완료 가능 | exit 누락과 별개로 error를 실패로 판정 |
| 높음 | 최근 10개에서 빠진 검증 이벤트가 재등장하면 새 통과로 인정 | 제한된 호출 ID 이력을 따로 유지해 오래된 중복 이벤트를 새 검증으로 세지 않음 |
| 높음 | 실행기에 SIGTERM을 보내면 정리 경로를 거치지 않아 Worker가 남을 수 있음 | Ctrl-C와 같은 정리 경로로 보내고 호출자의 신호 핸들러 복원 |
| 보통 | 숫자·빈 객체·알 수 없는 JSON도 비활성 시간을 갱신 | 인정한 구조·세션·유형의 이벤트만 활동 시간 갱신 |
| 보통 | 정확한 외부 스킬 경로에 들어간 `*`, `?`가 더 넓은 권한 패턴으로 해석될 수 있음 | 정규화한 경로의 와일드카드를 실행 전 거부 |
| 낮음 | 지시 파일을 전부 읽은 뒤 8 KiB 제한 확인 | 최대 8,193바이트만 읽어 제한 초과 판정 |
| 낮음 | 가짜 Python CLI의 site 초기화가 짧은 테스트 시간 제한에 영향을 줌 | 표준 라이브러리만 쓰는 테스트 대역에 현재 Python과 `-S` 사용 |

공개 검증 기록은 최근 10개 명령으로 유지한다. 내부 도구 ID 이력은 최대 10,000개로 제한하며,
추적 한도 초과는 완료 판정을 차단한다. 수정으로 추가 모델 요청이나 외부 런타임 의존성은 생기지 않는다.
기존 모델 우선순위, auto/manual/off, 일반 Worker 권한, checkout/config 잠금과 제출 형식은 유지했다.

## 실제 검증 결과

환경은 Linux, Python 3.13.5, Node.js v22.16.0이다. 실제 OpenCode 대신 가짜 CLI를 실행했다.

| 검사 | 관측 결과 |
| --- | --- |
| 원본 기본 테스트 | 39개 중 38개 통과, 활동 타임아웃 테스트 1개 오류 |
| 원본에 신규 회귀 테스트 적용 | 19개 메서드 실행, 하위 사례 포함 assertion 실패 21건. 오류 0건 |
| 수정본 전체 테스트 | 기존 39개 + 신규 19개 = 58개 통과, skipped 0개 |
| 수정본 반복 확인 | 최종 수정 후 두 차례 연속 58개 통과 |
| 실제 프로세스 대역 | SIGTERM 정리, 기존 핸들러 복원, 리더 종료 뒤 같은 그룹의 자식 정리 확인 |
| 제출 계약 | 실제 JS 제출 함수를 실행해 Python 검증과 수락·거부 비교. SDK는 인터페이스 대역 |
| 정적 검사 | Python 컴파일, JS 구문, 스킬 형식, 문서의 로컬 링크 확인 통과 |

테스트 수, assertion 실패 수, 결함 수는 서로 다른 지표다. 신규 테스트 일부는 수정 전에도
통과하는 보존 조건을 확인한다. 원본 타임아웃 오류는 테스트 대역의 `-S` 시작 방식으로 해소됐으며,
제품의 기본 300초 비활성 제한이나 선택적 hard timeout을 늘리지 않았다.

```sh
python3 -m unittest discover -s scripts -p 'test_*.py' -v
python3 -m compileall -q scripts
node --check assets/submit-result.mjs
```

재현 코드는 `scripts/test_audit_regressions.py`에 보존했다. Node.js가 없으면 JS 계약 검사 한 개가
skipped이므로 건너뜀도 확인한다. 테스트 중 provider 호출과 설치된 실제 SDK 검증은 하지 않는다.

## 스킬 평가와 가독성 개선

명시적 사용 조건, Head/Worker 역할 분리, 자기완결적인 짧은 지시, 단일 세션,
좁은 결과 확인, 측정 한계를 구분한 점은 목적에 맞다. 반면 좋은 문구가 있어도 런처가
거짓 완료를 반환하면 신뢰하기 어렵다. 이번 수정은 그 결정론적 부분을 보강한 것이다.

`SKILL.md`는 **대상 → 실행 → 종료·실패 → 결과 확인 → 보고**의 5단계, 83줄로 정리했다.
선택 사항을 표로 모으고 지시 예시, 8 KiB 제한, 최상위 status 우선 규칙을 추가했다.
UI 설명과 기본 요청도 한국어로 바꿨다. 사람용 개요는 README, 상세 설정은 별도 참고 문서에 둔다.
원본 5,121바이트에서 5,764바이트로 늘었다. 가독성 개선이 토큰 절감의 증거라고 주장하지 않는다.

[스킬 평가 기준](skill-evaluation.md)에 호출·거부·실패·불완전 증거 등 12개 행동 시나리오와
Head 단독/기존/수정 스킬 비교 방법을 적었다. 이는 **미실행 실험 명세**이며 LLM 평가 점수가 아니다.
현재 판단은 “실행 신뢰성을 회귀 검사한 스킬 후보”다. 실제 사용량·품질 우위까지 입증한 것은 아니다.

## 남은 한계

**통합과 효과:** 실제 OpenCode/SDK/provider, macOS, 다른 Python 버전, GitHub Actions CI는
이번 실행 검증에 포함되지 않는다. 호출 정확도, 코드 품질, Head 사용량·비용 절감은 별도 검증이 필요하다.

**프로세스와 보안:** 권한 프로필은 OS 샌드박스가 아니다. 허용된 shell·MCP와 상속된 환경은
신뢰 경계로 남는다. SIGKILL, 다른 그룹으로 이탈한 자식, 호스트의 종료 거부, 메인 스레드 밖의
신호 처리는 보장하지 않는다. 정상 CLI 종료도 모든 백그라운드 작업 종료를 증명하지 않는다.
재실행 전에 남은 실행 상태를 확인한다. 활동이 계속되는 세션에는 기본 총 상한이 없다.

**프로토콜과 증거:** 알려지지 않은 새 이벤트 유형은 완료를 차단하므로 CLI 버전 변경 시
실제 JSONL 표본과 제출 SDK를 확인해야 한다. 현재 공식 CLI 코드와 사용자 설치 버전을 같다고 가정하지 않았다.
`changed`는 Worker의 보고이며 독립 diff가 아니다. exit 0과 구조화 제출도 요구사항 충족을 증명하지 않는다.
고위험 변경에는 Head의 좁은 추가 확인이 필요하다.
